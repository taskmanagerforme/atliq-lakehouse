# AtliQ batch lakehouse: architecture

## 1. Why OLTP and OLAP are separate

OLTP is for production, which basically is for writing data and is good at writing it, but not meant for analysis. For that we need OLAP, where we can aggregate large number of rows on a regular basis. Also OLAP, we will do the updation once in a day on a D minus one basis, not on live, since this is batch update, I guess, not live streaming.
Most OLAP is structured in such a way that it is easier to analyze huge amounts of data, aggregate them, etc., related to analysis. Most of OLAP structures are in columnar storage, whereas most of the OLTP structures are in row level storage.
If we ran reports directly on the OLTP database, the heavy queries would slow down checkouts, because it is the same database production writes to, so analysis would affect the live shop. Also, the OLTP tables are normalised, so there would be multiple joins that need to be done, which is difficult when working with multiple tables and analysing the data. So we reshape it into a star schema with fact and dimension tables (fact_sales, dim_customer, dim_product, dim_date, plus fact_web_sessions), which needs far fewer joins and is easier to deal with.

## 2. How the control table and watermarks drive the nightly sync

The watermark is a bookmark kept for each table in the control table. Every time the sync runs, it records up to when that table has been copied, so the next run uses it as a reference and copies only the next set of rows, the data that changed since then.
updated_at means the last time the row changed, and created_at is the timestamp when the row was first created. Orders and payments use updated_at because their rows change (for example, an order goes Placed -> Delivered -> Returned). order_items uses created_at because a line never changes once written. The watermark for a table gets updated only if that table's copy succeeded. If not, it doesn't get updated, so the next run picks the same rows up again.
The control table has one row per table. customers and products are loaded in full every night (copied whole), because they are small and cheap to reload. orders, order_items and payments are loaded incrementally: only rows where the watermark column is newer than last_loaded_at are copied into bronze/<table>/ingest_date=<date>/. When the copy succeeds, the watermark is set to the time the run started, not the time it ended, so rows that arrive while the run is going are picked up the next night instead of being missed. On the first run (2026-11-14) the watermark was 1900-01-01, so all 10,020 orders were copied; after that only changes are copied.

## 3. What happens on a quiet night

A quiet night is a day or time where we have no new data due to some external scenario. Because of this the job would fail and we would receive an alert. In order to avoid this, we set up a guard which will know that there is no data available today, and will skip the process of reading it, but we will take a note of it in the logs (dq_log) that no data was available on this particular day and it has been skipped. But we will still receive the alerts in case there is an error other than this. Here the reading step gets skipped because there is no data in Bronze, but the job still runs and succeeds, and the step from Silver to Gold still runs. Silver data remains the same, which results in the Gold data remaining the same as well: the quiet night's Gold is the same as the previous day's. Which is simply idempotent in practice.

## 4. How I proved idempotency

From what I understand of idempotency, if you're running the job again and again, the data doesn't get appended. It appends only if there is new data, and if there is no new data, there is no append coming up with the existing tables. As in, there are no duplicate rows getting added because there is idempotency. And here, if you run the job again, there won't be any duplicate rows showing up, which explains the process that the current workflow is idempotent.
We already have something similar in the quiet night case, where running from Silver to Gold gives the same result if there is no change in Silver, because the process is idempotent.
This works because Silver uses MERGE on the business keys (order_id, order_item_id, payment_id): a new key is inserted, an existing key is updated only if the incoming row is newer, and anything else is ignored. Gold is rebuilt by dbt from Silver every run, so it always matches Silver.
I proved it in two ways. First, two runs of the job on 2026-11-13 gave identical results: 22,959 fact rows and 39,392,719.00 gross revenue both times (atliq.silver.run_audit). Second, the first ADF batch on 2026-11-14 contained all 10,020 orders, yet Silver went from 10,000 to exactly 10,020 orders (the 20 new ones), and the 5 orders the simulator had changed now show Returned: they were updated in place, not duplicated. (The 39.39M includes Cancelled orders; the checkpoint figure 32,424,661.00 excludes them.)
